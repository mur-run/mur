# Official FreeBSD 15.1 amd64 release and pkg support

**Status:** Approved in conversation on 2026-09-20; not yet implemented.
**Scope:** Native FreeBSD 15.1/amd64 build and test coverage, a mandatory GitHub Release tarball, a downloadable FreeBSD package, release orchestration, platform gates, and user documentation.
**Out of scope:** MUR Hub/GUI on FreeBSD, arm64 FreeBSD, FreeBSD 15.0 or 14.x guarantees, automatic service installation, a MUR-operated package repository, and claiming `pkg install mur` before a port is accepted into the FreeBSD Ports Collection.

## 1. Goal and support contract

MUR will treat FreeBSD 15.1 on amd64 as an officially supported CLI platform. Every tagged release must include these assets in the same GitHub Release as the macOS, Linux, and Windows assets:

- `mur-x86_64-unknown-freebsd.tar.gz`
- a FreeBSD package produced by the package tools, published with the stable release-facing name `mur-<version>.pkg`

Both contain the existing shipped CLI binary set:

- `mur`
- `mur-mcp-server`
- `murmurd`
- `mur-agent-runtime`
- `mur-research-gateway`

A release is incomplete until the FreeBSD build, tests, tarball, package, and checksums all succeed. Failure or timeout leaves a draft GitHub Release; it must not update Homebrew or publish crates.io follow-up work.

“Official” means native build and verification on FreeBSD 15.1, not merely that Rust can cross-compile the workspace. Platform-specific features without a FreeBSD implementation must return an explicit unsupported result. They must not silently use Linux paths, commands, service managers, or sandbox behavior.

## 2. Chosen architecture

### 2.1 Responsibilities

GitHub Actions remains the release coordinator and the source of truth for whether a release is published. Cirrus CI owns the native FreeBSD lane because GitHub-hosted Actions has no FreeBSD runner.

For a version tag:

1. GitHub Actions validates that the tag matches the workspace version.
2. GitHub Actions creates or reuses a **draft** GitHub Release for that tag.
3. Existing GitHub Actions jobs build the macOS, Linux, Windows, and Hub artifacts.
4. Independently, Cirrus runs a native FreeBSD 15.1 amd64 task for the same tag.
5. Cirrus tests and uploads the FreeBSD tarball and `.pkg` directly to the draft release.
6. A GitHub Actions finalizer waits for the Cirrus check attached to the tagged commit, verifies the two expected FreeBSD assets, downloads them, and generates one `checksums.txt` over all release binary/install assets.
7. Only after those gates pass does the finalizer publish the draft release.
8. Homebrew and crates.io jobs retain `needs: release-finalize` success gates, so they cannot run for a draft or failed release.

This avoids making Cirrus the release authority and avoids a second public release. The draft is the rendezvous point for artifacts from both CI systems.

### 2.2 Idempotency and ownership

All release jobs are retry-safe:

- Draft creation reuses a draft with the same tag instead of creating a duplicate.
- Cirrus replaces assets with the exact expected FreeBSD names when rerunning the same tag.
- The finalizer replaces `checksums.txt` and then publishes the existing draft.
- A rerun against an already published release verifies it and does not create another release.

Only GitHub Actions may change a release from draft to published. Cirrus may upload the two FreeBSD assets but may not publish, edit notes, retag, or delete the release.

## 3. Cirrus FreeBSD lane

A root `.cirrus.yml` defines a tag-only FreeBSD task using the FreeBSD 15.1 image family and amd64 architecture. Pull requests and ordinary branch pushes may run a secret-free build/test variant later, but they must never receive the upload credential or mutate a release.

The tag task:

1. Checks out the exact tagged commit.
2. Installs the documented native build prerequisites through `pkg` (Rust toolchain, Node.js for generated web assets, protobuf, CMake, Clang, and native libraries required by the resolved workspace).
3. Builds the release workspace natively for `x86_64-unknown-freebsd`; it does not masquerade a Linux cross-build as FreeBSD support.
4. Runs the applicable workspace unit/integration tests.
5. Executes `--version` for all five shipped binaries from the build output.
6. Creates `mur-x86_64-unknown-freebsd.tar.gz` from exactly the canonical five-binary list.
7. Extracts that tarball into a clean directory and repeats all five `--version` smoke tests from the extracted files.
8. Builds the FreeBSD package and checks it as described in §4.
9. Uploads exactly the tarball and `.pkg` to the existing draft GitHub Release.

The shipped binary set is owned by `release/binaries.toml`, with this schema:

```toml
schema = 1

[[binary]]
name = "mur"
package = "mur-core"

[[binary]]
name = "mur-mcp-server"
package = "mur-mcp-server"

[[binary]]
name = "murmurd"
package = "mur-daemon"

[[binary]]
name = "mur-agent-runtime"
package = "mur-agent-runtime"

[[binary]]
name = "mur-research-gateway"
package = "mur-research-gateway"
```

A repository helper reads this manifest and emits either names or Cargo package arguments. GitHub Actions, Cirrus, tar/zip/pkg assembly, smoke tests, updater-consistency tests, and Homebrew checks must call that helper; CI YAML must not carry a second `BINARIES` value. `mur-core/tests/release_packaging.rs` is changed from parsing `release.yml` to parsing this manifest and comparing it with the updater's required siblings.

### 3.1 Native package-build feasibility gate

`poudriere` is the preferred acceptance environment, but this design does **not** assume that Cirrus supports its jail, privilege, storage, and filesystem requirements. Before implementing release orchestration, a secret-free spike on the selected FreeBSD 15.1 Cirrus image must record:

- whether the task has the root privileges needed by poudriere;
- whether ZFS is available, and whether an approved UFS-backed poudriere setup works if it is not;
- jail creation, package bootstrap, available disk, cold-cache duration, and peak disk usage;
- whether nested jail/chroot operations survive Cirrus task isolation;
- the exact image family and package repository configuration used.

The spike has three outcomes, in preference order:

1. **Full poudriere in Cirrus:** use a clean FreeBSD 15.1 amd64 jail for every package release.
2. **Lightweight Cirrus package build:** use the port framework or staged install plus `pkg create` in Cirrus, then run install/check/uninstall tests in a clean disposable environment. A separate maintainer or FreeBSD-hosted poudriere run is mandatory before upstreaming the port; Cirrus must not claim poudriere validation.
3. **No reliable clean package environment:** permit tarball-only CI rehearsals while the package lane is repaired, but block official-support enablement and public release. The `.pkg` and Ports submission remain blocked rather than weakening their acceptance claims.

`poudriere -n` is not treated as a magic no-jail fallback: the spike must prove the exact mode and isolation actually used. The selected outcome and measured timings are committed to the implementation plan before `.cirrus.yml` or release finalization is enabled.

### 3.2 Timing and task split

The initial finalizer budget is **240 minutes**, not 120. The spike and prerelease rehearsal record cold- and warm-cache duration separately. If the p95-equivalent observed duration from rehearsals exceeds 180 minutes, Cirrus is split into fixed-name `freebsd-release-tarball` and `freebsd-release-pkg` tasks so compilation/smoke-test failures are distinguishable from package-environment failures. Both checks remain mandatory.

The finalizer uses bounded exponential polling (30 seconds, then 60 seconds, capped at 120 seconds) and reports failures as:

```text
FreeBSD release gate failed: check=<name> state=<state> elapsed=<minutes>m missing_assets=<comma-separated names or none>
```

A timeout is reported with `state=timeout`; it leaves the release in draft.

## 4. FreeBSD pkg support

Package support lands in two stages because a downloadable package and acceptance into the official FreeBSD repository have different owners and timelines.

### 4.1 Stage one: release-attached package

The repository gains a FreeBSD port overlay containing the normal port metadata (`Makefile`, `distinfo`, `pkg-descr`, and an explicit plist or generated equivalent). It builds from the immutable tagged source archive, installs the same five binaries under `${PREFIX}/bin`, and declares build/runtime dependencies rather than assuming a developer machine.

The workspace version is the sole version input. Version and filenames are derived as follows:

| Git tag | Workspace version | Tarball | Release-facing package |
|---|---|---|---|
| `v1.2.3` | `1.2.3` | `mur-x86_64-unknown-freebsd.tar.gz` | `mur-1.2.3.pkg` |
| `v1.2.3-rc.1` | `1.2.3-rc.1` | `mur-x86_64-unknown-freebsd.tar.gz` | `mur-1.2.3-rc.1.pkg` |

The leading `v` exists only in the tag and download path; it is never part of the package filename or internal package version. The package metadata version must equal the workspace version exactly after applying only the documented FreeBSD `pkg` version syntax conversion, if `pkg version -t` proves a conversion is required for a SemVer prerelease. That conversion helper and its table-driven stable/prerelease tests become the sole owner of the mapping; no CI shell snippet may improvise it.

Cirrus uses the package-build mode proven by §3.1. If full poudriere is available, it uses a clean FreeBSD 15.1 amd64 jail. Otherwise it uses the documented lightweight path and labels the evidence accurately. The resulting package is copied/renamed at the release boundary to `mur-<version>.pkg`; the package’s internal origin, version, ABI, dependency metadata, and file ownership remain those generated by the FreeBSD package tools.

Acceptance checks are mandatory:

- the selected clean build completes without leftovers or plist errors;
- `pkg check` passes;
- install into a clean test environment succeeds;
- all five installed binaries answer `--version`;
- package metadata reports the tagged MUR version and FreeBSD amd64 ABI;
- uninstall succeeds and leaves no owned files behind;
- the release-facing filename is exactly `mur-<version>.pkg`;
- `ldd` is captured for every shipped binary and every non-base shared object is represented by package dependency metadata.

The current dependency audit already shows bundled SQLite and rustls for most network paths, but `mur-daemon` currently enables `tokio-tungstenite/native-tls`; therefore the package must be treated as potentially dependent on non-base libraries until a native FreeBSD build plus `ldd` proves otherwise. The package manifest is generated from staged binaries with `pkg create`/ports tooling and then checked against `ldd`; it is not maintained by guesswork.

A release-attached package is advertised for direct `pkg add <URL>` **only if it has no unresolved non-base runtime dependencies**. Because direct URL `pkg add` is not the supported dependency-resolution route, if non-base dependencies remain MUR must choose one before stage-one publication:

1. remove or statically link those dependencies where licensing and FreeBSD support permit; or
2. publish a signed MUR pkg repository and document repository bootstrap plus `pkg install mur`.

The initial design excludes operating such a repository, so unresolved non-base dependencies block the release-attached `.pkg`; they do not become a manual prerequisite list. When the dependency gate passes, installation is documented as:

```sh
pkg add https://github.com/mur-run/mur/releases/download/vX.Y.Z/mur-X.Y.Z.pkg
```

The documentation must not describe this as `pkg install mur`: `pkg install` searches configured repositories, while a release URL is installed with `pkg add`.

### 4.2 Stage two: FreeBSD Ports Collection

After stage one is stable, the same port is prepared for submission to the FreeBSD Ports Collection. The submission must pass the project’s current port linting and poudriere matrix expected by FreeBSD reviewers. A named maintainer owns update requests and responds to port review.

Only after the port is accepted and has reached FreeBSD’s package builders may MUR document:

```sh
pkg install mur
```

The official FreeBSD package can lag a GitHub Release because FreeBSD controls its build and publication schedule. That lag does not block MUR’s GitHub Release; the release-attached `.pkg` remains the immediate supported route.

MUR will not initially operate a custom signed package repository. Doing so would add long-lived signing keys, repository indexes, hosting, rotation, and recovery obligations merely to make `pkg install` available earlier.

## 5. Release synchronization and failure handling

### 5.1 Cirrus completion gate

The finalizer polls the tagged commit’s GitHub Checks API for the Cirrus task/check corresponding to the FreeBSD release lane. Before implementation, a secret-free tag spike records the exact check name and `check_suite.app.slug` returned by the API in this section and in a machine-readable release policy file. The expected task names are fixed as `freebsd-release` or, when split under §3.2, `freebsd-release-tarball` and `freebsd-release-pkg`; renaming one is a release-contract change requiring the policy and its tests to change in the same commit. The finalizer matches both the recorded Cirrus app slug and fixed check name, so an unrelated successful check cannot satisfy the gate. If Cirrus changes its GitHub App identity, the gate fails closed with the observed and expected slugs; maintainers update the policy only after review.

The wait is bounded at 240 minutes and uses the polling/backoff policy in §3.2. Outcomes are:

| State | Finalizer behavior |
|---|---|
| Cirrus check succeeds and both assets exist | Continue verification and publish |
| Check fails, is cancelled, or concludes non-success | Fail; retain draft |
| Check or assets do not appear before timeout | Fail; retain draft |
| Assets exist but names, version, size, or archive contents are wrong | Fail; retain draft |
| Existing-platform core build fails | Fail under the existing build gate; retain draft |

The finalizer emits the exact missing check or asset in its error. It never silently drops FreeBSD and publishes a partial release.

### 5.2 Artifact handoff and checksums

GitHub build jobs never upload public release assets directly. They upload immutable workflow artifacts with `actions/upload-artifact`; Cirrus alone uploads its two assets to the draft rendezvous. A renamed `release-finalize` job has explicit `needs` edges to `validate-version`, `build`, `package-macos`, `hub-macos`, and the draft-creation job, and uses `if: always()` only so it can preserve/report a failed draft—not to publish around a failed dependency. It first requires every mandatory `needs.*.result` to be `success`, downloads all GitHub workflow artifacts, waits for and downloads the Cirrus draft assets, validates the complete expected asset set, then creates and uploads `checksums.txt`. Only its final step flips the existing draft to published.

This replaces the current `release` job behavior, which uses `needs: [build, package-macos, hub-macos]` but gates only on `needs.build.result`; under the new contract a failed macOS package or Hub job cannot be silently omitted. Homebrew and crates.io jobs depend on `release-finalize`, never merely on draft creation.

Cirrus does not publish a competing checksum file. After collecting GitHub Actions artifacts, the GitHub finalizer downloads the two FreeBSD assets from the draft and generates the single authoritative `checksums.txt` over every published tarball, zip, pkg, and dmg. It verifies that each expected FreeBSD filename appears exactly once before publishing.

A checksum mismatch, duplicate asset, zero-byte asset, or missing FreeBSD entry is a release failure. There is no “ignore FreeBSD” input on the release workflow; recovery is to fix/rerun the failed lane or deliberately revoke the support policy in a reviewed change.

### 5.3 Failed-draft cleanup

Failed drafts are retained as forensic evidence by default. A separate manual `release-cleanup` workflow accepts an exact tag, displays the draft ID and asset list, and deletes only a release that is still a draft and whose tag exactly matches the input; it never deletes a published release or git tag. The runbook also documents the equivalent audited `gh release delete <tag> --yes` command. No age-based automatic deletion runs initially, avoiding removal while a 240-minute gate or incident investigation is active.

A `workflow_run`/`repository_dispatch` callback may replace polling later, but it does not remove the need to authenticate the Cirrus app/check and verify assets. The first implementation keeps one bounded finalizer because Cirrus and GitHub tag jobs start independently and the draft is their explicit rendezvous.

## 6. Credentials and trust boundaries

Cirrus receives a fine-grained GitHub token stored only as an encrypted Cirrus secret. It is scoped to `mur-run/mur` with the minimum repository contents/release write permission needed to upload assets.

The secret is exposed only when all of these are true:

- the build is for a version tag in the canonical repository;
- the commit belongs to that tag;
- the task is the named release task;
- the build is not from a fork or pull request.

Scripts must not echo the token, place it in command arguments visible to unrelated processes when avoidable, persist it in artifacts/caches, or pass it to poudriere. Upload tooling receives it only for the release-upload step. GitHub Actions’ built-in token remains responsible for creating and publishing the draft.

Pinned CI action versions and a fixed FreeBSD 15.1 image family make the environment reviewable. Package versions installed from the selected FreeBSD repository are recorded in logs; MUR does not claim bit-for-bit reproducibility unless separately implemented and verified.

## 7. Platform behavior

The implementation audits `target_os` and OS-name branches that currently divide the world into macOS, Linux, and Windows. FreeBSD receives explicit behavior where portable Unix support is valid, and an explicit unsupported path otherwise.

Required outcomes include:

- update asset resolution maps `(freebsd, x86_64)` to `mur-x86_64-unknown-freebsd.tar.gz`;
- install-source detection gains an explicit `Pkg` source by inspecting the running executable/package ownership rather than merely noticing that `pkg` exists;
- for `Pkg`, `mur update --check` and `mur update` do not download or replace the tarball: both print `Installed via FreeBSD pkg. Run: pkg upgrade mur` and return successfully;
- tarball/manual FreeBSD installs remain `Other` and may use the existing checksum-verified self-update path;
- updater sibling handling covers the same packaged binary contract as other platforms;
- Unix sockets/process handling is enabled only where its implementation is valid on FreeBSD;
- Linux-only service management (`systemd`), sandboxing, notifications, paths, and commands are never selected on FreeBSD;
- `mur doctor` identifies FreeBSD accurately and reports unsupported integrations instead of “unrecognised platform” where the CLI itself is supported;
- daemon/service auto-install remains unsupported unless a separate rc.d design is approved;
- GUI export and desktop integration remain unsupported and say so directly.

No hardcoded POSIX installation path is introduced into Rust logic; platform paths use Rust path APIs. Shell used by packaging remains POSIX `sh` compatible where possible, while FreeBSD-specific tooling stays isolated in its packaging lane.

## 8. Tests and acceptance

### 8.1 Repository tests

Before CI implementation, a committed `docs/platforms/freebsd-audit.md` inventories every Rust `target_os`, `target_family`, `cfg!`, and `std::env::consts::OS` branch that can affect the five CLI binaries. Each entry records: portable as-is, add explicit FreeBSD behavior, or deliberately unsupported with its user-facing error. This audit is the implementation checklist; it is not replaced by a broad compile attempt.

Platform-independent decision logic is extracted into pure functions or small traits that accept an OS/architecture/capability input. Table-driven tests for FreeBSD, Linux, macOS, and Windows run on every normal CI host; tests must not try to fake Rust’s compile-time `cfg(target_os)` setting. Conditional compilation and actual syscall/tool behavior are covered by native jobs: FreeBSD-only compile/integration/package tests run in Cirrus, while existing OS-native lanes retain their platform tests.

Add tests that lock down:

- FreeBSD amd64 release asset naming;
- pkg-owned FreeBSD installs return the `pkg upgrade mur` hint, while manual FreeBSD installs retain tarball self-update;
- the canonical five-binary package set and consistency with updater expectations;
- explicit unsupported behavior for service/sandbox/desktop features not implemented on FreeBSD;
- archive contents: exactly the five expected executable names, with no test helpers;
- release workflow semantics: draft first, Cirrus success plus both assets required, final publication last;
- FreeBSD port metadata version and package filename derivation.

Existing Linux, macOS, and Windows tests continue to pass. Cross-platform branches must retain explicit coverage so adding FreeBSD does not collapse Windows into a generic “other Unix” path.

### 8.2 Native release acceptance

A release is accepted only when the FreeBSD 15.1 native lane proves:

1. workspace compilation and applicable tests pass;
2. all five build-tree binaries pass `--version`;
3. all five extracted tarball binaries pass `--version`;
4. poudriere builds the package cleanly;
5. package install/check/uninstall tests pass;
6. GitHub draft contains both exact FreeBSD asset names;
7. final `checksums.txt` includes both assets;
8. the release becomes public only after the Cirrus check succeeds.

A one-time pre-release rehearsal uses a disposable version/tag reserved for this purpose, for example `v0.0.0-freebsd-test.1`, with the workspace version changed to the exact matching SemVer in the rehearsal commit. It executes this checklist:

1. create/reuse the draft release;
2. let Cirrus upload the tarball and, if §3.1 passed, the `.pkg`;
3. let the finalizer collect every GitHub artifact, regenerate checksums, and—only in the success rehearsal—publish the release as a prerelease;
4. verify all archive/package installs and asset names from the public prerelease;
5. rerun with an intentional FreeBSD failure and verify the release remains draft while Homebrew/crates.io are skipped;
6. delete the disposable tag, draft/prerelease, and rehearsal-only commit/branch according to the repository’s retention policy.

The rehearsal must not use an ordinary release version, publish crates, or update Homebrew. Its measured durations and Cirrus check identity are copied into this design/implementation record before official release enablement.

## 9. Documentation and rollout

README/release documentation is written before enabling the release jobs and states:

- supported platform: FreeBSD 15.1 amd64 CLI;
- unsupported scope: Hub/GUI, arm64, older FreeBSD releases, automatic service installation;
- tarball download and checksum verification;
- release-package installation with `pkg add` only when the §4.1 dependency gate passes;
- the exact runtime dependency evidence from native `ldd`/package metadata, not a placeholder list;
- removal with `pkg delete mur`;
- updater behavior: pkg-owned installs use `pkg upgrade mur`, manual tarball installs may use `mur update`;
- `pkg install mur` only after the official port/package is available, including the possibility of repository lag.

Rollout order:

1. land `release/binaries.toml`, its helper, and manifest-consistency tests;
2. write `docs/platforms/freebsd-audit.md`, then land platform compatibility and host-independent tests;
3. run the secret-free Cirrus/poudriere feasibility spike, record its selected outcome, check identity, disk use, and timing;
4. land the Cirrus native tarball lane and rehearse it without publication;
5. land the port overlay and the package checks allowed by the proven §3.1 path; do not advertise `.pkg` until the runtime-dependency gate passes;
6. land draft/finalize orchestration and perform both successful and intentional-failure prerelease rehearsals;
7. enable official tagged releases;
8. submit the proven port upstream as a separately tracked maintenance task.

The first official release is not advertised until the native tarball and package installation tests have passed on FreeBSD 15.1 and the draft-release failure path has been demonstrated.
