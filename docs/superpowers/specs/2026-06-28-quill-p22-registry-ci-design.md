# Quill P2.2 — skill-registry repo + signing/validation CI (the trust companion)

**Status:** Design / spec
**Date:** 2026-06-28
**Codename:** quill (skills sibling of feather)
**Builds on:** quill P2 (#531, per-agent registry install + verify-on-install) and P2.1 (#533, publisher trust-roots + TOFU + drift). This is the **server/registry-side companion** those two deferred.

---

## 1. Problem & the (small) real gap

P2/P2.1 shipped the **client**: install a registry skill onto an agent, verify its DSSE signature against a pinned publisher keyring, detect drift. But two things are missing for the feature to actually deliver value:

1. **The registry repo doesn't exist.** `DEFAULT_REGISTRY = https://github.com/mur-run/skill-registry.git` (`mur-core/src/cmd/skill_registry.rs`) points at a repo that was never created. The client fail-softs (`mur skill search` warns "registry search failed"), so today there is nothing to install *from*.
2. **The pinned trust anchor is a placeholder.** `MUR_OFFICIAL_PUBLISHER_KEY_FP = "ed25519-0fficial"` (P2.1) is not a real key, so every real signer classifies `Untrusted` (fail-safe: over-prompts for `--yes`).

### What ALREADY exists (reuse map — verified)

| Capability | Where |
|---|---|
| `mur skill publish <path>` — signs the manifest (`sign_manifest`), forks `mur-run/skill-registry`, clones the fork, writes `skills/<name>/versions/<v>.yaml`, computes `content_sha256` into `index.yaml`, branches/commits/pushes, opens the PR via `gh` | `mur-core/src/cmd/skill_publish.rs` |
| Publisher identity (offline key) | `~/.mur/publisher-identity.key` via `resolve_publisher_identity()` → `AgentIdentity::{load,generate,save}`; fingerprint = `ed25519-<first 8 hex of SHA256(pubkey)>` (`dsse::keyid_from_pubkey`) |
| Per-manifest DSSE sign/verify | `mur_common::skill::sign::{sign_manifest, verify_manifest}` |
| `content_sha256(&manifest)` | `mur_common::skill::content_sha256` |
| Index + entry schema the CI must emit | `mur_common::skill::registry::{RegistryIndex{schema_version,updated_at,skills:BTreeMap<name,RegistrySkillEntry>}, RegistrySkillEntry{latest,description,publisher,category,tags,content_sha256,install_count}}` |
| Client install + verify + scan + trust + drift | P2/P2.1 (`skill_registry_add.rs`, `skill_verify.rs`, `skill_signer_trust.rs`, `publisher_trust.rs`) |

**Conclusion:** the publisher CLI flow is built. P2.2 is **(a) the registry repo scaffold + a validation CI, (b) the official key + const bump, (c) trust bootstrapping** — almost all in the *separate* `mur-run/skill-registry` repo, with a one-line const change in mur-common.

## 2. Decisions (from brainstorming)

- **Key custody: offline key + `mur skill publish` (already the model).** The publisher signs locally with their own offline `~/.mur/publisher-identity.key`; the signature travels in the manifest. **CI never holds a signing key** — it only *validates*. (Matches TUF "offline root" best-practice; Sigstore keyless was rejected — it needs online Rekor/Fulcio and breaks P2.1's offline pinned-key verification.)
- **Scope: mur-side + registry scaffold blueprint.** This spec covers the tiny mur-repo change (const bump; any `publish` gap-fills) **and** a complete blueprint for the `mur-run/skill-registry` repo (layout, CONTRIBUTING/PR flow, CI workflow, seed). **Operator actions (kept out of code):** creating the GitHub repo, generating the official signing keypair, and holding its private key.

## 3. Design

### 3.1 `mur-run/skill-registry` repo layout (blueprint)

```
index.yaml                       # RegistryIndex — CI-generated, authoritative
skills/
  <name>/
    versions/
      <semver>.yaml              # a signed SkillManifest (publisher_signature embedded)
publishers/
  mur.pub                        # the MUR-official publisher PUBLIC key (identity.pub)
  <handle>.pub                   # optional: other publishers' public keys (informational)
README.md                        # what this is; how trust works
CONTRIBUTING.md                  # the publish flow (below)
.github/workflows/validate.yml   # the validation CI (§3.3)
```

`index.yaml` is **generated by CI**, never hand-edited (so a contributor can't forge `content_sha256`/`publisher`).

### 3.2 Publish flow (already implemented; documented for CONTRIBUTING.md)

A publisher runs `mur skill publish path/to/skill.yaml`, which: validates → signs with their offline key → forks + clones `skill-registry` → writes `skills/<name>/versions/<v>.yaml` → opens a PR. A human maintainer reviews the PR (GitHub identity = publisher authentication, the "trusted-publishing" identity layer adapted to a git registry); merge triggers CI to regenerate `index.yaml`.

### 3.3 Validation CI (`.github/workflows/validate.yml`) — the core new work

On every PR and on push to the default branch, for each added/changed `skills/**/versions/*.yaml`:
1. **Parse + schema-validate** the manifest (`parse_canonical` + `validate`). Reject on failure.
2. **Require a present, internally-valid signature** — `verify_manifest(&m, publisher_signature)` must pass (DSSE self-consistent). Reject unsigned / invalid. *(CI does not own a trust-root; it enforces "signed", and the client enforces "signed by a trusted/TOFU'd key" via P2.1.)*
3. **Security scan** — `scan_skill`; **block merge** on blocking findings (`has_blocking_findings()`), mirroring the client's fail-closed posture so poisoned skills never reach the index.
4. **Recompute `content_sha256` authoritatively** from the file and **(on default-branch push) regenerate `index.yaml`** — CI writes `content_sha256`, `publisher` (from the signature's key), `latest` (max semver), `category`, `tags`, preserving `install_count`. A contributor cannot forge these because CI overwrites them.
5. **Filename ↔ manifest agreement** — `<semver>.yaml` must equal `manifest.version`; `skills/<name>/` must equal `manifest.name` (and be `is_valid_skill_name`). Reject path/traversal mismatches.

Implementation: a small Rust validator (a `mur`-invoking step, or a tiny script reusing the published `mur` binary — e.g. `mur skill validate` + a new `mur skill registry-index` regen subcommand) so the CI shares the exact parse/scan/hash code the client trusts. **Lean:** add a `mur skill registry-index <repo-dir>` helper (mur-core) that regenerates `index.yaml` from `skills/**`, reused by both CI and local testing — single source of truth for the index format.

### 3.4 mur-repo changes (small)

- **Bump `MUR_OFFICIAL_PUBLISHER_KEY_FP`** (`mur-common/src/skill/publisher_trust.rs`) to the real fingerprint of the official publisher key, once generated. (Operator generates the keypair; this const + `publishers/mur.pub` in the registry carry the public half.)
- **`mur skill registry-index <repo-dir>`** (new, §3.3) — regenerate `index.yaml` from `skills/**/versions/*.yaml`; pure, reuses `content_sha256`/`parse_canonical`/`RegistryIndex`. Used by CI and `mur skill publish` consistency.
- **Gap-fill `mur skill publish`** only if review finds it omits a step the CI now requires (e.g. ensure it does NOT pre-write a `content_sha256` the CI would just overwrite — or have it leave that to CI). Verify against the implemented flow; minimal.

### 3.5 Trust bootstrapping

- Generate the official Ed25519 publisher keypair **offline** (operator). Commit only `publishers/mur.pub` to the registry; keep the private key offline.
- Set `MUR_OFFICIAL_PUBLISHER_KEY_FP` to its fingerprint and ship in the next client release. From then on, skills signed by the official key install **silently** (Trusted); all others are `Untrusted` → TOFU/`--yes` (P2.1), exactly as designed.

## 4. Security model

- **Offline key custody:** the only signing keys are publishers' offline keys; **CI holds no key** and cannot be coerced into signing. (Eliminates the CI-secret-exfiltration class.)
- **CI = validate-only, fail-closed:** unsigned/invalid-signature/poisoned/version-mismatched skills are rejected at PR; `content_sha256` is recomputed by CI (un-forgeable by the contributor); `index.yaml` is CI-generated.
- **Publisher authentication:** GitHub PR + maintainer review / CODEOWNERS (identity layer). The official key is pinned in the client; everyone else is TOFU (P2.1).
- **Defense in depth:** the signature + hash + scan are checked at PR time **and re-checked client-side on install** (P2/P2.1) — the registry is not trusted blindly.
- **What it does NOT stop** (documented): a malicious skill from a publisher a user explicitly TOFU-trusts; compromise of an official offline key (mitigated by the P2.1 revocation list, shipped with client updates). No transparency log (Sigstore) — accepted for local-first.

## 5. Testing

- **mur-repo:** unit-test `mur skill registry-index` (regenerate a fixture `skills/**` → assert `index.yaml` content_sha256/latest/publisher correct; reject a name/version-mismatched file). Reuse the P2 fixture-registry layout.
- **Registry repo (blueprint, validated locally):** a `validate.yml` dry-run against a fixture PR — one clean signed skill (passes), one unsigned (rejected), one with an injection payload (rejected by scan), one with `version` ≠ filename (rejected).
- **End-to-end (operator):** generate the official key → `mur skill publish` a seed skill → CI builds `index.yaml` → client `mur agent skill registry-add` installs it **silently** (Trusted, once the const is bumped).

## 6. Non-goals

- Sigstore keyless / Rekor transparency log (needs online verify; breaks local-first).
- A hosted HTTP/OCI registry (the git-clone model stays).
- Automated/CI-side signing (offline-key model is deliberate).
- Key-rotation ceremony tooling (note: rotation = generate new key, update `publishers/mur.pub` + const + revoke old via P2.1 `revoked` list; full tooling deferred).
- Creating the GitHub repo / generating the official private key (operator actions).
- Namespace-ownership enforcement beyond maintainer PR review (a future server feature).

## 7. Open questions

- Per-publisher namespaces (e.g. `skills/<publisher>/<name>/...`) to prevent name squatting, or flat `skills/<name>` with maintainer-arbitrated names? (Lean: flat for v1 + maintainer review; revisit if squatting appears — matches the current `skill_yaml_path` layout, so flat avoids a client change.)
- Should CI also publish a **signed** `index.yaml` (official key signs the index) so the client can verify the index itself, not just per-manifest? (Lean: defer — per-manifest DSSE + client-side re-verify already covers artifact trust; a signed index is a TUF-lite add-on for later if registry-host compromise becomes a concern.)
- `install_count` source of truth — CI preserves it, but who increments it? (Lean: out of scope; a later telemetry/server feature. Keep the field, leave it 0/manual.)
