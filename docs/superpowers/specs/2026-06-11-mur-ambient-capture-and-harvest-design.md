## TL;DR — one inversion

**Today's `mur in`/`mur out` is "press record first, hope for value later"; this redesign flips it to "always recording, harvest afterwards."** `mur in` stops being a gate (capture is ambient and always on once hooks are installed); `mur out` changes from "stop recording" to "review the harvest inbox." That is the only real conceptual change — everything else stacks on the approved workflow-engine v2 spec and code that already exists.

New mental model: **`in` = put attention in (mark this session as important), `out` = take the learning out (harvest)**.

---

## 1. Diagnosis — why the current design cannot be saved

1. **Doubly fragile recording chain.** `mur in` (`mur-core/src/cmd/session.rs:291`) only writes `~/.mur/session/active.json`. Actual event capture depends on the AI agent voluntarily calling `mur session record` per event (`dispatch.rs:205` → `session.rs:614`), as instructed by the `mur-in` skill. Recording therefore requires **two simultaneous preconditions**: the user remembers to run `mur in` *before* the session (prospective memory — the weakest form of human memory), and the agent complies for the whole session. Either breaks → the session is lost forever.

2. **The value moment defaults to nothing.** The `mur out` interactive menu (`session.rs:415-419`) defaults to **Skip** (`.default(2)`). Even when the user did everything right, pressing Enter discards the session.

3. **Single global active session.** `active.json` is global — two parallel Claude sessions interleave into one recording file (same bug class as the known two-agents-one-worktree collision).

4. **The ambient channel already exists — and is wasted.** The installed hooks (`~/.mur/hooks/on-prompt.sh` etc., generated by `mur init --hooks`) run `mur hook prompt|tool|stop` on **every** prompt and tool call, already writing `NormalizedEvent`s (with `session_id`, `tool_called`, `tool_input`; five providers: claude/gemini/cursor/copilot/opencode — `mur-core/src/inject/event.rs:16-43`) to `~/.mur/queue/events.jsonl`. **MUR is already recording ambiently; the data simply never reaches the learning pipeline.** `mur in` guards a parallel, more fragile track.

5. **Workflow-engine v2 is approved but unimplemented.** The v2 spec settled: Workflow = Skill with `category: Workflow`, Pattern removal, run-ledger, LLM extraction advisory-only (SkillsBench: LLM-authored skills +0.0pp vs human-curated +16.2pp). `git log` confirms P1a–P8 have not started. **This redesign does not overturn v2 — it re-plumbs `in`/`out` in front of it** and solves v2's own cold-start problem (its bootstrap path was the manual `mur-in`/`mur-out` flow — i.e., the broken thing).

6. **The server side is more complete than assumed.** mur-server already has `/api/v1/workflows` CRUD + publish, `/api/v1/commander/workflows/sync` + `executions` reporting, and `/api/v1/core/fleet/{entity_type}` push/pull. On the Rust side, `fleet_sync.rs` already syncs the skills dir, and **per-skill `events.jsonl` set-union merge is already implemented** (`fleet_sync.rs:261`) — v2's "multi-machine ledger sync is out of scope" assumption is already half-solved.

| Source | Relevant conclusion |
|---|---|
| [Anthropic — Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) | Skills are human-authored with progressive disclosure (MUR already has the isomorphic 3-layer injector); "agents creating skills" is explicitly future work, not present |

| [mem0 — Memory Operations](https://docs.mem0.ai/core-concepts/memory-operations) | Three-stage distillation: extract → conflict-resolve (latest-truth-wins) → store; inference on by default; visible/editable/deletable memory is the trust precondition |
| ChatGPT memory / Claude Code auto-memory (industry norm) | **No mainstream product asks the user to "press record first"** — all do ambient capture + post-hoc distillation + user review |
| Durable execution (Temporal / Inngest / GH Actions, established practice) | Trustworthy server-run workflows require: runs as first-class objects (history, logs, retries), HITL gates that pause/resume, versioning, audit trails |

Industry consensus matches v2 amendment A1 (LLM extraction advisory; promotion requires human curation). This design keeps that principle.

## 3. Design

### 3.1 Capture: always on (abolish "start recording" as an action)

Promote the existing ambient hook channel to the sole capture source:

- `mur hook prompt|tool|stop` writes directly to `~/.mur/session/recordings/<session_id>.jsonl`, keyed by the hook payload's `session_id` (incidentally fixing parallel-session interleaving). `active.json` no longer gates recording.
- Events gain the v2 Layer 1 enrichment: `exit_code`, `working_dir`, `git_branch` (PostToolUse payloads carry tool results).
- The `Stop` hook starts parsing `transcript_path` from its payload (currently unused) to add assistant-turn summaries — the main driver of extraction quality.
- `session/scrub.rs` (exists) runs at write time to strip secrets. New config:

```yaml
session:
  capture: ambient          # ambient | manual | off (per-project overridable)
  retention_days: 14        # daemon GC; builds on existing mur session remove
harvest:
  auto_gate: true           # murmurd runs the gate on session end
  llm: local-first          # local | cloud | off (Notes-spec optional-LLM rule)
```

### 3.2 `mur out` = harvest, not "stop"

```
$ mur out
◆ 3 sessions since last harvest (2 worth reviewing)

  1. "fix hub dark-mode contrast"   47 events · 22m · repeatable ✓
     → proposed workflow: hub-css-fix-verify (5 steps, 1 variable)
  2. "release v2.22.20"             31 events · 11m · repeatable ✓
     → proposed workflow: mur-release (4 steps, matches existing 87%)
       ⚠ near-duplicate of existing `mur-release` — propose merge

  [a]ccept & edit  [s]kip  [d]iff  [q]uit
```

- Flow: session ends (Stop hook) → murmurd runs the **gate** in the background (existing `session_worth_analyzing` heuristics + v2 config thresholds; LLM gate optional) → passing sessions produce a **proposal** in `~/.mur/inbox/workflow-proposals/`.
- `mur out` reviews that inbox. Accept writes a draft (`provenance: llm`; first human edit flips to `hybrid`; never auto-promoted, per v2 amendment A1). **The default action flips from Skip to Review.**
- Directly compatible with the companion workflow-nudge spec: the nudge payload *is* the proposal; Hub/companion pushes "I noticed you deployed with the same steps 3 times this week — save as a workflow?"; the CLI fallback *is* `mur out`.
- mem0-style dedup: proposals are first compared against existing workflows (vector + step-skeleton similarity); high similarity proposes merge / confidence bump instead of a new file — v2's cross-session aggregation, landed as suggestions (A1's P5b reclassification).

### 3.3 `mur in` = mark (keep the command, replace the semantics)

`mur in` is not removed (back-compat, skills, muscle memory). It becomes an **importance marker**: sets `marked: true` on the current session's meta; the harvest gate passes marked sessions unconditionally (skips heuristics). `mur out --action analyze|export|skip` keeps its current behavior (applied to the most recent session) so scripts don't break.

### 3.4 Execution & lifecycle: follow v2, do not reinvent

DAG steps, unified executor, `runs.jsonl` run-ledger feeding the existing `skill::lifecycle::next_state`, Broken fast-path, `mur skill audit` — all unchanged from v2 (P2–P4, P8). This design contributes the piece v2 lacks: **a reliable session supply side** (ambient capture dissolves v2's cold-start dependency on the manual flow).

### 3.5 Workflows on MUR Server

Principle: **execution always stays local (local-first is the moat); the server does four things — registry, run history, scheduled dispatch, governance/audit.** All four stack on existing parts:

1. **Registry (publish/install).** `mur workflow publish/install` already uses `/api/v1/workflows` (YAML blob + visibility + version). Only change: the published object is the `category: Workflow` skill YAML, reusing DSSE signing (`skill/sign.rs`); server adds a `kind` filter field. Dashboard list/install pages unchanged.
2. **Run history (the basis of trust).** Local `runs.jsonl` events push via fleet sync (per-skill `events.jsonl` set-union merge **already implemented**); the dashboard shows cross-machine run stats per workflow (success rate, last success, which step breaks). Team-level lifecycle: a workflow is team-Stable only after N members' successful runs — governance data, not decoration.
3. **Scheduled dispatch (the server never executes; it dispatches).** Server cron (schedule_handler exists) does **not** run in the cloud: it produces a Commander-signed dispatch envelope (`SignedEnvelope` Ed25519, already used by C7 Slack bridge) → A2A to the target agent runtime → local execution → `POST /api/v1/commander/executions` report (endpoint exists). `needs_approval` steps trigger Hub HITL (the Phase 3 real-HITL-trigger work in flight lands exactly here).
4. **Feedback loop (Commander → local lifecycle).** Use the frozen Signal v1 wire protocol (2026-05-18 spec): implement mur-daemon's `POST /v1/signals/batch` (the gap that spec names), so Commander's execution evidence feeds local skill stats — remote runs count toward promotion/demotion.

One lifecycle line: **personal draft → (human curation) → Stable → publish to team registry → (team run evidence) → team Canonical → Commander scheduled dispatch + audit.** Every segment maps to a subsystem that already exists.

### 3.6 Privacy & resources

- Scrub at write time (existing module) + `retention_days` GC + per-project `capture: off` override — three safety valves for ambient.
- The gate defaults to heuristics; LLM only participates when a local model is available or the user explicitly enables cloud (Notes-spec rule) — ambient ≠ token burn.
- Hook latency: appending one JSONL line is O(1); the prompt hook is already async — typing feel unaffected.

### 3.7 Token budget & cloud-LLM cost model

**Recording and analysis are fully decoupled: capture costs zero tokens.** Hooks do pure local I/O (JSON parse + JSONL append); no LLM is ever called per event. Tokens can only be spent at harvest time, behind gates:

| Stage | Frequency | Default cost |
|---|---|---|
| Capture (hooks → JSONL) | every event | **0** (local I/O only) |
| Gate ("worth harvesting?") | once per session end | **0** — heuristics (`session_worth_analyzing` + config thresholds), not an LLM |
| Extract (produce a proposal) | only gate-passing sessions | the only token spend, governed by `harvest.llm` |

With `harvest.llm: local-first` (the default), extraction uses a local model when available and **does not call cloud at all unless the user explicitly opts in**. Ambient capture therefore costs cloud-LLM users nothing by default. A single Extract is no more expensive than today's `mur out --action analyze` (same call, same input); the design changes the *frequency* (extraction actually happens), and frequency is what the following three defenses bound.

**Cloud cost defenses (normative):**

1. **Lazy extraction.** When `harvest.llm: cloud`, session end runs only the zero-cost heuristic gate and queues *candidates* (skeleton + metadata, no LLM) in the inbox. The expensive Extract call is deferred to the moment the user opens `mur out`, then batched across pending candidates. If nobody opens the inbox, nothing is spent — token spend is tied to user attention, not to recording volume.
2. **Dedup before extract.** Step-skeleton similarity against existing workflows and pending proposals is computed locally *before* any Extract call. A recurrence of a known procedure never re-extracts — it bumps the existing entry's `usage_count`/confidence (the v2 cross-session signal) at zero token cost. Only genuinely novel skeletons reach the LLM.
3. **Hard caps.** New config (all per Mandatory Rule #1, no hardcoding):

```yaml
harvest:
  llm: local-first            # local | cloud | off
  max_llm_calls_per_day: 10   # Extract budget; gate is always free
  max_extract_input_tokens: 12000   # skeleton truncated beyond this
  model_tier: cheap           # cheap | default — extraction output is human-curated anyway,
                              # so a Haiku-class model is sufficient; errors are caught at review
```

   Sessions marked via `mur in` consume the daily budget first (user-declared importance outranks heuristic ordering).

**Order-of-magnitude estimate** (explicit cloud opt-in, heavy user): ~10 sessions/day, heuristic gate passes 2–3, Extract ≈ 5–15k input / ~1k output tokens each → ~30k tokens/day. On a Haiku-class tier that is **roughly $1–2/month**; even a Sonnet-class tier stays around $4–5/month. The input is never the raw recording — the noise filter + literal-stripping skeletonization (v2 Layer 2) runs first, which is what keeps Extract input bounded.

### 3.8 Attention channels & notification policy

**Why this section exists:** this redesign eliminated prospective memory on the capture side; a pull-only inbox (user must remember to run `mur out`) would reintroduce the same bug on the harvest side — and unreviewed proposals are worthless (§7 Weaknesses: curation is the value gate). Proactive surfacing is therefore part of the design, not an add-on. The question is channel choice. Note that the companion nudge spec (2026-05-29) already provides most of the machinery: idle-tick delivery, DND/Focus check via `voice/dnd.rs`, `nudge.daily_cap`, snooze/dismiss `NudgeLedger`, CLI fallback.

**Channel hierarchy (normative):**

| Tier | Channel | Rationale |
|---|---|---|
| **1** | **SessionStart hint** (new; ships in W2) | MUR's unique attention surface: the hook already injects context at session start — add one line: `📥 2 workflow proposals pending — run 'mur out'`. Guaranteed seen, zero interruption (a task boundary is the cheapest interruption point), no OS permission, and it reaches CLI-only users — the majority before Hub adoption |
| **2** | **Companion bubble** (per nudge spec Unit 4, unchanged) | Idle tick + DND check + three inline actions (Save / Not now / No thanks) — one fewer context switch than notification→dashboard, and it is the branded differentiating surface; ceding proactive moments to OS notifications dilutes the companion's reason to exist |
| **3** | **OS system notification** (dormant-user fallback only; optional, deferred) | Fires only when: high-confidence proposals pending **and** no mur-hooked session for `os_dormant_days` (tier 1 cannot fire) **and** Hub not running (tier 2 cannot fire). A re-engagement channel, never a daily channel |

**Tier-3 rules (if/when built):**
- **Digest, never per-proposal** ("MUR organized 3 repeatable workflows for you").
- **Deep link to the review view** (Hub inbox item or dashboard inbox page), never the dashboard home — every removed step matters.
- **Self-silence rule (most important):** 2 consecutive ignored notifications (shown, not clicked) → stop sending entirely; fall back to passive mentions in `mur out`/`mur doctor`. Notification fatigue ends with the user disabling the channel at the OS level — a channel that never recovers; silence yourself first.
- Frequency cap independent of `nudge.daily_cap` (≤1/week); idle + DND checks reuse `voice/dnd.rs`; zero tokens (content comes from skeleton candidates — §3.7 lazy extraction runs only after click-through).

```yaml
notify:
  session_start_hint: true    # tier 1 — one-line pending hint at SessionStart
  os_fallback: auto           # auto | off — tier 3, dormant users only
  os_dormant_days: 3
  os_max_per_week: 1
  os_self_silence_after: 2    # consecutive ignored → stop
```

**Decision:** tier 1 ships in W2 (~half a day, solves ~80% of the attention problem). Tier 2 follows the existing nudge spec. Tier 3 is deferred until post-W2 data shows a dormant cohort that tiers 1–2 cannot reach (if SessionStart hint drives sufficient inbox-open rate, tier 3 is never built).

| Phase | Content | Main touch points | Est. |
|---|---|---|---|
| **W1 capture flip** | Hooks write per-session recordings + Layer 1 enrichment + scrub + retention GC; `mur in` becomes marker | `cmd/hook.rs`, `session/mod.rs`, `inject/event.rs`, config | 3–4 d |
| **W2 harvest inbox** | murmurd gate → proposals; `mur out` review UI; near-dup merge; companion nudge hookup; §3.7 cost defenses (lazy extract, dedup-before-extract, caps); §3.8 tier-1 SessionStart hint | `cmd/session.rs`, daemon, `create_draft_workflow` (exists) | 1 wk |

| **W4 server runs** | Fleet-sync run events; dashboard run history; team lifecycle view | `fleet_sync.rs` (mostly exists), mur-server dashboard | 1 wk |
| **W5 scheduled dispatch + HITL** | Server cron → Commander signed dispatch → local execute + report; implement `/v1/signals/batch`; Hub HITL for `needs_approval` | mur-daemon, commander handler, Hub (after Phase 3 merges) | 1.5–2 wk |

W1+W2 changes how the product *feels* within two weeks: no command to remember; after a session MUR proactively says "here's what I learned — keep it?" That is the payoff moment.

## 5. Risks

- **Proposal noise (the biggest risk):** gate thresholds all in config (v2 rule); repeatedly-skipped proposal types get down-weighted; under-report rather than nag.
- **Privacy perception:** ambient must be explicitly disclosed at `mur init --hooks` + one-line off switch; `mur session list/show/remove` already provide visibility and deletion.
- **W3 ordering dependency:** W2's accept writes the current `Workflow` type first; the P7 migration converts to skills — keeps W2 from being blocked by the v2 big lift.
- **Commander is a separate closed-source team:** freeze the W5 dispatch envelope format first (as Signal v1 was frozen), then develop in parallel.

## 6. Ecosystem impact — structural, not incremental

**This design fixes the ecosystem's most fatal problem: the learning subsystem has no supply.** Evidence: all 160 patterns have `injection_count == 0` (v2's own autopsy); lifecycle promotion thresholds are practically unreachable for a single user; v2's cold-start section depends on the manual `mur in`/`mur out` flow — whose double fragility is exactly why supply never arrives. The whole engine — `evolve/`, `retrieve/`, skill lifecycle, the 3-layer injector — is currently **idling**. Ambient capture connects the fuel line: every agent session across all five providers becomes raw material.

How it propagates through each ecosystem layer:

- **Inter-agent knowledge flow becomes real.** Harvested `category: Workflow` skills are injected into all agents via the existing runtime injector, transfer between agents via skill peers/A2A, and replicate across machines via fleet sync. The pipes exist today; nothing flows through them. Harvest is the missing intake.
- **Export-to-app (consumer wedge) value density.** The 5-minute wow is "export your agent as a companion app and hand it to someone." What makes an agent worth giving away is its **accumulated procedural knowledge**, not a prompt + model binding shell. Without harvest you export a template; with harvest you export "the agent I trained for three months" — that is what makes it viral.
- **Commander (enterprise moat) gets something to govern.** Provenance (session → llm draft → human curated → signed publish → governed dispatch) is a complete evidence chain — exactly the "where did this automation come from, who approved it, how often does it run, when did it break" that enterprises pay for. Without the run-ledger and provenance chain, Commander governs air.
- **Monetization alignment.** Pro's first paid point is syncing the *evolved* fleet — harvest is the machine that manufactures evolved state. The more an agent learns, the stronger the cross-device sync pull; Team's shared registry also needs workflow supply to not be an empty shelf.
- **Companion retention moments.** "I noticed you deployed with the same steps three times this week — save it?" is one of the few proactive utterances a companion can make that is genuinely useful. The nudge spec is designed; it lacks proposal supply.

Honest counterpoint: this does **not** directly strengthen runtime capability (A2A, sandbox, voice are untouched); all benefit propagates indirectly via content supply. And if the curation UX fails and users let the inbox rot, noisy skills degrade agents below the no-skill baseline (the Library Drift finding) — the v2 amendment's human-curation gate is not bureaucracy; it is this design's seatbelt.

## 7. SWOT vs competitors

Compared against: Claude Code (auto-memory/skills), Devin (playbooks/knowledge), Cursor (memories), mem0/Zep/Letta (memory infra), Archon (workflow harness), n8n/Zapier (workflow SaaS).

### Strengths
- **The only player closing the full loop:** ambient capture → human curation → executable workflow → evidence-driven lifecycle → cross-machine sync → governed dispatch, in one local-first stack. Competitors each own one segment: mem0 does facts not procedures; Devin's playbooks are hand-written; Claude Code memories aren't executable; n8n executes but never learns from your behavior; Archon requires hand-written YAML. The positioning spec's capability matrix shows "auto workflow mining from behavior" as MUR ✓ vs everyone ✗ — this design turns that ✓ from half-built into real.
- **Cross-vendor neutrality:** hooks already cover claude/gemini/cursor/copilot/opencode. Claude Code's memory only helps Claude; Cursor's only helps Cursor. MUR is the only one aggregating learning above all tools — vendors will not aggregate each other's data, so this position is structurally closed to them.
- **Local-first legitimizes ambient.** "Record everything" is only sellable when data never leaves the machine. Cloud competitors doing ambient capture step on a privacy landmine; MUR records locally, distills locally, at ≈0 marginal cost — a free tier cloud rivals structurally cannot match.
- **Evidence-driven retirement:** run-ledger + outcome-driven skill retirement is the link Library Drift research says the whole industry neglects; MUR's lifecycle state machine is already written — it lacks only data, which this design supplies.
- **Speed to ship:** hooks, skill subsystem, fleet sync (incl. events.jsonl set-union), commander executions API all exist; W1+W2 deliver perceptible product change in two weeks.

### Weaknesses
- **Value is gated on curation discipline.** SkillsBench: LLM-authored +0.0pp, human-curated +16.2pp — if users don't review the inbox, the feature is objectively worthless. The inbox can become another ignored notification pile (the #1 product risk, not an engineering risk).
- **Install friction vs built-ins.** Requires `mur` + `mur init --hooks`; Claude Code memory works out of the box. Neutrality's price is being forever third-party.
- **Hook APIs are someone else's foundation.** Five vendors' hook schemas are moving targets; any one breaking change severs a supply line — a permanent maintenance tax.
- **Solo-dev bandwidth vs the W1–W5 surface**, plus extraction quality depends on local models (weak machines fall back to heuristics-only gating).

### Opportunities
- **The "Plaid of agent memory" position.** Model vendors are absorbing the harness layer (the positioning spec already concedes that fight), but they will not do cross-vendor memory aggregation — neutral memory is the vacuum vendors leave behind.
- **agentskills.io open standard:** `category: Workflow` skills can export to the standard format — "procedural memory you can take to any agent tool"; interop is the neutral player's best weapon.
- **Rising governance/compliance demand** (EU AI Act et al.): procedure provenance + tamper-evident audit is precisely the Commander chain's pitch; enterprises pay to know "who taught my agent this."
- **Local models keep improving = extraction quality rises for free.** The design is bound to local-first and rides the hardware/model curve.

### Threats
- **Biggest: Anthropic/OpenAI going native.** Anthropic has publicly stated agents creating/editing/evaluating skills is their direction; once Claude Code ships built-in session→skill extraction, MUR's single-tool story is absorbed. The only defenses: cross-vendor aggregation (they won't), local privacy (they won't — it kills token revenue), governance depth (they haven't). Marketing must lead with these three, not with "auto-learn workflows" itself.
- **"Always recording" perception risk.** Even fully local, one misunderstanding is hard to wash off — explicit consent at install, one-line disable, and visible/deletable sessions must be first-class features, not documentation footnotes.
- **Memory-infra companies extending from facts to procedures** (mem0/Zep/Letta), and the tail risk of vendors tightening hook/ToS access for third parties.

**One-line verdict:** this design lands the differentiator the positioning spec already marked "half-built, product work = polishing" (record-and-mine) and is the supply side of the ecosystem flywheel; the SWOT hinges not on the feature itself but on (a) whether the curation UX makes people actually press accept, and (b) telling the cross-vendor + local-privacy + governance story fast enough — because the single-tool version of this feature will almost certainly be built by the model vendors.
