MUR Ambient Capture & Harvest
「mur in / mur out / Server Workflow」重新設計

永遠在錄、事後收穫 — 把學習子系統的供給端接上燃料管
Status: proposed · Date: 2026-06-11 · Author: david + Claude Fable 5 · 對應 spec: 2026-06-11-mur-ambient-capture-and-harvest-design.md
TL;DR — 一個翻轉:今天的 mur in/mur out 是「先按錄影、後求價值」;重新設計把它翻成「永遠在錄、事後收穫」。mur in 不再是開關(錄製常駐),mur out 從「停止錄製」變成「審閱收件匣」。這是唯一真正的概念變更,其餘全部疊在已核准的 workflow-engine v2 spec 和現有程式碼上。
新的心智模型:in = 把注意力放進來(標記),out = 把學到的拿出來(收穫)。

1現況診斷 — 為什麼今天的設計救不起來

① 雙重脆弱的錄製鏈。mur in(session.rs:291)只寫 active.json;真正的事件寫入靠 AI 代理自己呼叫 mur session record(dispatch.rs:205)。錄到東西需要兩個前提同時成立:使用者事前記得 mur in(前瞻記憶,人類最弱的記憶形式)+ 代理整場乖乖逐事件回報。任一斷掉,session 永遠消失。
② 價值時刻的預設是放棄。mur out 互動選單(session.rs:415-419)預設選項是 Skip。即使全做對了,按 Enter 的結果是什麼都不留下。
③ 全域單一 active session。兩個平行 Claude session 會交錯寫進同一份錄製檔,資料直接污染。
④ 最諷刺:ambient 通道早就存在。已安裝的 hooks 在每一次 prompt/tool call 都跑 mur hook prompt|tool|stop,事件已以 NormalizedEvent(含 session_id,支援 claude/gemini/cursor/copilot/opencode 五家)寫進 ~/.mur/queue/events.jsonl。MUR 已經在 ambient 錄製,只是錄的東西沒餵給學習管線。
⑤ v2 spec 已核准但未動工。Workflow = category: Workflow 的 Skill、移除 Pattern、run-ledger、LLM 抽取僅供建議(SkillsBench:LLM 自產 +0.0pp vs 人工 curation +16.2pp)。git log 確認 P1a–P8 都還沒開始。本設計不推翻 v2,而是把 in/out 重新接到它前面,順便解掉 v2 自己的 cold-start 問題。
⑥ Server 端零件比想像中齊。/api/v1/workflows CRUD+publish、Commander executions 回報、fleet push/pull 都已存在;Rust 端 per-skill events.jsonl 的 set-union 合併已實作(fleet_sync.rs:261)— 多機 run-ledger 同步其實已被解掉一半。

來源與本設計相關的結論
Anthropic — Agent SkillsSkill 以人工撰寫為主、漸進式揭露三層(MUR 已有同構實作);「代理自己寫 skill」明確列為未來式
Devin — Playbooks程序(playbook)是手寫的;自動學的只有事實型 Knowledge — 程序與事實分開治理

業界共識與 v2 修正案 A1(LLM 抽取僅 advisory、晉升需人工 curation)完全一致 — 重新設計沿用此原則。

3新設計

3.1 Capture:錄製常駐(廢除「開始錄製」這個動作)

  • mur hook prompt|tool|stop 直接寫 ~/.mur/session/recordings/<session_id>.jsonl,以 hook 的 session_id 分檔 — 順帶根治平行 session 交錯。active.json 不再是錄製閘門。
  • 事件按 v2 Layer 1 增補:exit_code、working_dir、git_branch。
  • Stop hook 開始解析 transcript_path(現在完全沒用到),補上 assistant turn 摘要 — 抽取品質的主要來源。
  • 寫入時即跑 session/scrub.rs(已存在)去除秘密。
session:
  capture: ambient          # ambient | manual | off(per-project 可覆寫)
  retention_days: 14        # 到期由 daemon GC
harvest:
  auto_gate: true           # session 結束時由 murmurd 跑 gate
  llm: local-first          # local | cloud | off

3.2 mur out = 收穫(harvest),不再是「停止」

$ mur out
◆ 3 sessions since last harvest (2 worth reviewing)

  1. "fix hub dark-mode contrast"   47 events · 22m · repeatable ✓
     → proposed workflow: hub-css-fix-verify (5 steps, 1 variable)
  2. "release v2.22.20"             31 events · 11m · repeatable ✓
     → proposed workflow: mur-release (4 steps, matches existing 87%)
       ⚠ near-duplicate of existing `mur-release` — propose merge

  [a]ccept & edit  [s]kip  [d]iff  [q]uit
  • Session 結束 → murmurd 背景跑 gate(啟發式 + config 閾值,LLM 可選)→ 產生 proposal 放 ~/.mur/inbox/workflow-proposals/。
  • mur out 審閱收件匣:accept 寫入 draft(provenance: llm,人工編輯後轉 hybrid,永不自動晉升)。預設動作從 Skip 翻成 Review。
  • 與 companion workflow nudge spec 直接相容:nudge payload 就是同一份 proposal;CLI fallback 即 mur out。
  • mem0 式去重:proposal 先和既有 workflow 比對(向量 + 步驟骨架),相似度高提「合併/升 confidence」而非開新檔。

3.3 mur in = 標記(保留指令,換掉語意)

mur in 不刪(向下相容),變成重點標記:對當前 session 標 marked: true,harvest gate 對 marked session 直接放行。mur out --action analyze|export|skip 維持原行為,腳本不會壞。

3.4 執行與生命週期:照 v2 spec,不重新發明

DAG steps、unified executor、runs.jsonl run-ledger、餵進現有 lifecycle 狀態機、Broken fast-path、mur skill audit — 全部維持 v2 原案(P2–P4、P8)。本設計貢獻它缺的東西:穩定的 session 供給端(ambient capture 直接解掉 cold-start)。

3.5 MUR Server 上的 Workflow 故事

原則:執行永遠在本地(local-first 是護城河),server 負責四件事 — registry、run 歷史、排程派工、治理稽核。全部疊在現有零件上。
  1. Registry(發佈/安裝) — 沿用 /api/v1/workflows;published 物即為 category: Workflow skill 的 YAML,沿用 DSSE 簽章。
  2. Run 歷史(信任的基礎) — 本地 runs.jsonl 經 fleet sync push(set-union 合併已實作);dashboard 顯示跨機 run 統計;團隊層級 lifecycle:N 個成員 run 成功才升團隊 Stable。
  3. 排程派工(server 不執行,只派工) — server cron 到點 → Commander 簽章派工信封(Ed25519,C7 已用過)→ A2A 送 agent runtime → 本地執行 → POST /api/v1/commander/executions 回報。needs_approval 步驟觸發 Hub HITL(Phase 3 正在開發,時程剛好接上)。
  4. 回饋閉環 — 用已凍結的 Signal v1 wire protocol:補實作 mur-daemon 的 POST /v1/signals/batch,遠端 run 證據回灌本地 lifecycle。
個人 draft → (人工 curation) → Stable → publish 到 team registry → (團隊 run 數據) → 團隊 Canonical → Commander 排程派工 + 稽核

每一段都對應一個已存在的子系統。

3.6 隱私與資源

  • 寫入時 scrub + retention_days GC + per-project capture: off — ambient 的三道安全閥。
  • Gate 預設走啟發式,LLM 只在本地模型可用或明確開 cloud 時介入 — ambient ≠ 燒 token。
  • Hook 延遲:append 一行 JSONL 是 O(1),prompt hook 已是 async — 不影響打字手感。

3.7 Token 預算與雲端 LLM 成本模型

「錄」和「算」完全解耦:錄製本身 0 token。Hooks 是純本地 I/O(JSON 解析 + JSONL append),沒有任何逐事件的 LLM 呼叫。Token 只可能在收穫階段產生,且有三道閘門擋在前面。
階段觸發頻率預設成本
Capture(hooks 寫檔)每個事件0(純本地 I/O)
Gate(值得收穫嗎?)每場 session 結束一次0 — 啟發式規則,不是 LLM
Extract(產生 proposal)只有通過 gate 的 session唯一花 token 的地方,受 harvest.llm 控制

harvest.llm: local-first(預設)只用本地模型;雲端要使用者明確開啟才會碰 — 雲端用戶在預設值下 ambient 錄製一毛 token 都不花。單次 Extract 成本與今天的 mur out --action analyze 完全相同;新設計改變的是「頻率」,而頻率被以下三道防線綁死:

  1. Lazy extraction(延遲抽取)。harvest.llm: cloud 時,session 結束只跑零成本的啟發式 gate,把「候選」(骨架 + metadata,不經 LLM)排進收件匣;昂貴的 Extract 延後到使用者打開 mur out 那一刻才批次執行。沒人看收件匣就一毛不花 — token 花費和使用者的注意力綁定,不和錄製量綁定。
  2. 先去重、再抽取。和既有 workflow / 待審 proposal 的步驟骨架相似度比對在 Extract 之前本地完成。已知流程的重複出現永不重抽 — 只升既有條目的 usage_count/confidence(v2 的跨 session 訊號),零 token。只有真正新穎的骨架才會碰到 LLM。
  3. 硬上限。新 config(全部可調,符合 Mandatory Rule #1):
harvest:
  llm: local-first            # local | cloud | off
  max_llm_calls_per_day: 10   # Extract 額度;gate 永遠免費
  max_extract_input_tokens: 12000   # 骨架超過即截斷
  model_tier: cheap           # cheap | default — 抽取結果反正有人工 curation 把關,
                              # Haiku 級就夠;錯誤在審閱時被抓

mur in 標記過的 session 優先消耗每日額度(使用者宣告的重要性優先於啟發式排序)。

數量級估算(明確開 cloud 的重度用戶):一天 10 場 session、gate 放行 2–3 場、單次 Extract ≈ 5–15k in / ~1k out → 一天 ~30k tokens。Haiku 級 ≈ 每月 $1–2;Sonnet 級也只 $4–5/月。餵給 LLM 的永遠不是原始錄製檔 — noise filter + 去字面值骨架化(v2 Layer 2)先跑,Extract 輸入因此有界。

3.8 注意力通道與通知政策

為什麼需要這一節:本設計在 capture 端消滅了前瞻記憶;如果收件匣是純 pull(要記得跑 mur out),同一個 bug 只是搬到 harvest 端 — 而沒人審的 proposal 一文不值(curation 是價值閘門)。主動 surfacing 是設計的一部分,問題只在通道選擇。注意:companion nudge spec(2026-05-29)已提供大部分機制 — idle 偵測、DND/Focus 檢查、nudge.daily_cap、snooze/dismiss 帳本、CLI fallback。
順位通道理由
1SessionStart 注入提示(新增,W2 出貨)MUR 獨有的注意力面:hook 本來就在 session 開始注入 context,加一行「📥 2 workflow proposals pending — run mur out」。保證被看到、零打擾(task boundary 是中斷成本最低的時刻)、不需 OS 權限、CLI-only 用戶也吃得到
2Companion 氣泡(照 nudge spec Unit 4,不變)idle tick + DND 檢查 + 氣泡上直接三鍵 Save / Not now / No thanks — 比「點通知→進 dashboard」少一次 context switch,且是差異化資產;把主動時刻讓給 OS 通知會稀釋 companion 存在的理由
3OS 系統通知(只做沉睡用戶 fallback;optional、延後)觸發條件:有高信心 proposal 且 連續 os_dormant_days 天沒有 mur session(順位 1 沒機會觸發)且 Hub 沒在跑(順位 2 沒機會觸發)。是喚回通道,不是日常通道

順位 3 如果做,的規則:

  • Digest,絕不逐則(「MUR 整理了 3 個可重複的工作流程」)。
  • Deep link 到審閱頁(Hub 收件匣那一筆或 dashboard inbox view),不是 dashboard 首頁 — 少一步是一步。
  • 自殺規則(最重要):連續 2 次被忽略(顯示了但沒點)→ 自動停發,退回 mur out/mur doctor 的被動提及。通知疲勞的終局是使用者去 OS 設定永久關掉你 — 那個通道死了就回不來,寧可自己先閉嘴。
  • 頻率上限獨立於 nudge.daily_cap(≤1/週);idle + DND 複用 voice/dnd.rs;零 token(內容來自 skeleton candidates — §3.7 的 lazy extraction 在點進來之後才跑)。
notify:
  session_start_hint: true    # 順位 1 — SessionStart 一行提示
  os_fallback: auto           # auto | off — 順位 3,只打沉睡用戶
  os_dormant_days: 3
  os_max_per_week: 1
  os_self_silence_after: 2    # 連續被忽略 → 停發

決定:順位 1 在 W2 出貨(約半天,解掉 ~80% 的注意力問題);順位 2 照既有 nudge spec;順位 3 延後到 W2 上線後看數據 — 如果 SessionStart hint 的收件匣開啟率已夠高,順位 3 永遠不用做。

5風險

  • 最大Proposal 噪音:gate 閾值全走 config;連續被 skip 的 proposal 類型降權;寧可漏報不可騷擾。
  • 觀感隱私感受:mur init --hooks 時明示告知 + 一行 config 可關;mur session list/show/remove 提供可視性與刪除權。
  • 排序W3 依賴:W2 的 accept 先寫現行 Workflow 型別,P7 migration 一併轉 skill — 避免 W2 被 v2 大工程卡住。
  • 協作Commander 是閉源另一團隊:W5 派工信封格式比照 Signal v1 先 freeze 再並行開發。

6對 MUR Agent 生態的幫助 — 結構性的,不是加分題

這個設計解的是整個生態最致命的問題:學習子系統沒有供給。160 個 pattern 的 injection_count == 0(v2 親自驗屍)、lifecycle 晉升門檻對單人實際不可達、v2 cold-start 依賴的手動路徑正是餵不進資料的原因。evolve/、retrieve/、skill lifecycle、3-layer injector 這整套引擎現在是空轉的。Ambient capture 等於接上燃料管。
  • Agent 之間的知識流動成立了。收穫出的 workflow skill 走現有 runtime injector 注入所有 agent、走 skill peers/A2A 在 agent 間轉移、走 fleet sync 跨機複製。管道都在,缺的就是入水口。
  • Export-to-app 的價值密度。agent 值得送人的理由是它累積的程序性知識。沒有 harvest,匯出的是模板;有 harvest,匯出的是「我調教了三個月的 agent」— 這才有 viral 的理由。
  • Commander 拿到可治理的對象。Provenance(session → llm draft → human curated → signed publish → governed dispatch)是完整證據鏈 — 企業買單的正是「這個自動化是哪來的、誰核准的、跑了幾次、何時壞的」。
  • 變現模型直接受益。Pro 首個付費點是同步「已演化的 fleet」— harvest 正是製造已演化狀態的機器;Team 的 shared registry 也需要 workflow 供給才不是空櫃子。
  • Companion 的 retention 時刻。「我注意到你這週用同樣步驟 deploy 了三次,要存起來嗎?」是 companion 少數真正有用的主動發言。

誠實的反面:它不直接增強 runtime 能力(A2A、sandbox、voice 不受影響),效益全經「內容供給」間接傳導;若 curation UX 失敗、收件匣堆積,雜訊 skill 會讓 agent 劣化到比沒有還差(Library Drift 實證)— 人工 curation 閘門是這個設計的安全帶,不是官僚程序。

7SWOT vs 競品

比較對象:Claude Code(auto-memory/skills)、Devin(playbooks/knowledge)、Cursor(memories)、mem0/Zep/Letta(記憶基礎設施)、Archon(workflow harness)、n8n/Zapier(workflow SaaS)。

SStrengths 優勢

  • 唯一打通全鏈:ambient 擷取 → 人工 curation → 可執行 workflow → 證據驅動生命週期 → 跨機同步 → 治理派工,一條鏈在一個 local-first stack。競品各佔一段:mem0 只做事實、Devin playbook 手寫、Claude Code memory 不可執行、n8n 不會從行為學、Archon 要手寫 YAML。
  • 跨廠商中立:hooks 已接五家工具。廠商彼此不會幫對手聚合資料,這個位置他們結構上進不來。
  • Local-first 讓 ambient 正當:「全程錄製」只有資料不出機器才賣得出去;邊際成本 ≈ 0 的免費層,雲端對手撐不起。
  • 證據驅動退場:run-ledger + outcome-driven retirement 是全行業忽略的環節(Library Drift),MUR 狀態機已寫好,只缺數據。
  • 上市速度:hooks、skill 子系統、fleet sync、executions API 全部已存在;W1+W2 兩週見效。

WWeaknesses 劣勢

  • 價值卡在 curation 紀律。SkillsBench:LLM 自產 +0.0pp、人工 +16.2pp — 使用者不審收件匣,功能客觀上沒價值。收件匣可能變成另一個被忽略的通知堆(頭號產品風險)。
  • 安裝摩擦 vs 內建功能。要裝 mur + hooks;Claude Code memory 開箱即用。中立性的代價是永遠是「第三方」。
  • Hook API 是別人家的地基。五家 schema 都是移動標靶,任一家改版斷一條供給線。
  • 單人開發頻寬 vs W1–W5 面寬;抽取品質依賴本地模型。

OOpportunities 機會

  • 「agent 記憶的 Plaid」位置。模型廠商吸收 harness 層,但不會做跨廠商記憶聚合 — 中立記憶層是廠商留下的真空。
  • agentskills.io 開放標準:workflow skill 可輸出標準格式,「帶得走的程序記憶」— 互通性是中立玩家最好的武器。
  • 治理合規需求上升(EU AI Act 等):程序 provenance + 不可竄改稽核,企業願意為「誰教會了我的 agent」付錢。
  • 本地模型持續變強 = 抽取品質免費上升。設計綁定 local-first,搭硬體/模型曲線便車。

TThreats 威脅

  • 最大威脅:Anthropic/OpenAI 原生化。Anthropic 已公開說 agent 自建 skill 是方向;Claude Code 一旦內建 session→skill 抽取,單工具故事被吸收。防線只有三條:跨廠商聚合(他們不會)、本地隱私(他們不願 — 殺 token 營收)、治理深度(他們還沒)。
  • 「永遠在錄」觀感風險。即使全本地,被誤解一次很難洗白 — 明示同意、一行關閉、可視可刪必須是第一級功能。
  • 記憶基礎設施公司向程序延伸(mem0/Zep/Letta);廠商 ToS 收緊第三方 hooks 的尾部風險。
一句話總結:這個設計把定位 spec 裡寫著「already half-built、product work = polishing」的核心差異化(record-and-mine)真正落地,是生態飛輪的供給端;SWOT 的勝負手不在功能本身,而在 (a) curation UX 能不能讓人願意按 accept、(b) 跨廠商+本地隱私+治理這三條護城河講得夠不夠快 — 因為「單工具內的同款功能」幾乎確定會被模型廠商做掉。
