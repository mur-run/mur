# CAS Efficiency Results

**Status:** Pending — populate from `judge_stats.json` after `mur fleet judge --stats` is implemented

## Overview

The Content-Addressed Store (CAS) efficiency measures how effectively the parallel track merge process reuses identical function signatures and utility implementations across tracks. This avoids re-generating the same code multiple times when tracks diverge but then reconverge on the same logic.

## Expected Metrics

- **CAS Hit Rate:** ≥ 30% for codebases with repeated utility functions across tracks
- **Typical scenarios:**
  - Three parallel agents implementing a shared library: expect 40-50% CAS hits (many common utility functions)
  - Three agents on independent modules: expect 15-25% CAS hits (minimal shared functions)
  - High-complexity refactors: 60%+ CAS hits are possible

## Collection Method

After running a parallel fleet with `mur fleet judge --stats`:

```bash
python3 scripts/cherry_quality.py ~/.mur/fleets/<fleet-name>
```

Output from `judge_stats.json` (generated by `mur fleet judge --stats`):
- `cas_hit_rate`: Fraction of cherry-result functions matching content-addressed store
- `cost_ratio_vs_single`: Parallel execution cost ÷ single-agent cost

## Performance Tuning

If CAS hit rate is low (< 30%):
1. Add embedding-similarity pre-scoring to `mur-core/src/merge/judge.rs`
2. Cluster functions by semantic similarity before CAS lookup
3. Increase context window in track prompts to reduce spurious divergence

If cost ratio is high (> 2.5×):
1. Profile `mur fleet judge` timing per track
2. Reduce track parallelism (use 2 agents instead of 3)
3. Increase model parallelism (use batch inference via MLX)
